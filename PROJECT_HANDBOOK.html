Project at a Glance

The big picture in plain language, then the technical version.

1.1 What problem does this project solve?

Taking attendance by calling names is slow, and paper sign-in sheets are easy to cheat. A friend can sign for an absent student ("proxy attendance"). This project gives a classroom two digital ways to record that a student is present:

  1. Face check-in (the "biometric kiosk"). A laptop or tablet with a webcam sits at the door. The browser sends camera frames to the server, the server finds faces and recognises enrolled students, and the browser waits for each recognised student to blink before it records attendance. The blink check is there so that holding up a printed photo does not work.
  2. QR check-in. The teacher's screen shows a QR code that changes every 5 seconds. Students scan it with their phone camera, type their roll number, confirm their name, and attendance is recorded. Because the code keeps changing and expires quickly, a photo of it forwarded to a friend at home only works for a short time.

An administrator (teacher or staff member) signs in to enroll students, run the kiosk, show the QR code, see today's numbers on a dashboard, browse the attendance log, download it as a CSV spreadsheet file, or clear it.

1.2 Executive summary

In simple words

It is a website written in Python. Teachers log in, register students and take a few photos of each face. The server turns each photo into a list of 512 numbers that describes the face (an "embedding"), averages them, and stores the result. Later, at the classroom door, the camera page sends pictures to the server, which compares every face it sees with the stored lists of numbers and says who it is. The page then waits for that person to blink and marks them present. Students without the camera can instead scan a QR code that changes every few seconds.

Technical summary

A Flask monolith (one Python web application) created by an application factory app/__init__.pycreate_app()L12–59↗ with three blueprints (groups of routes): authentication/pages/QR tokens in app/routes/main.py, enrollment and student lookups in app/routes/student.py, and recognition/attendance/records in app/routes/attendance.py. Data lives in a relational database through SQLAlchemy (PostgreSQL in production, SQLite in tests) with three tables: admins, students, attendance.

Face detection uses MTCNN and recognition uses FaceNet (InceptionResnetV1, VGGFace2 weights) from the facenet-pytorch library running on CPU with PyTorch app/ai/facenet_model.py. Each student is stored as one L2-normalised 512-dimensional vector (JSON text in students.embedding). Matching is a single NumPy matrix–vector product app/ai/comparator.pyvectorized_matrix_match()L47–86↗. To keep the kiosk responsive, detection runs on every 4th frame and OpenCV CSRT trackers follow faces in between app/routes/attendance.pyrecognize_with_box()L94–235↗. Blink-based liveness runs in the browser app/static/js/recognize.jsanalyzeEyeLiveness()L108–154↗.

Admins authenticate with a signed session cookie (browser) or a JWT bearer token (API clients) app/routes/main.pyadmin_required()L91–123↗. QR codes carry short-lived tokens signed with itsdangerous app/routes/main.pycheck_qr_token()L229–245↗. Failed logins are counted in a cache that uses Redis when configured and an in-process dictionary otherwise app/extensions.pySafeCacheStoreL32–131↗. Prometheus metrics are exposed at /metrics app/metrics.pyinit_metrics()L41–69↗. The app runs under Gunicorn (1 worker, 4 threads) via run.py, ships with a Dockerfile, a Docker Compose stack, Kubernetes manifests and a GitHub Actions CI workflow, and (per your statement and the README link) is deployed on Render.

What it is not

There is no model training, no large language model (LLM), no retrieval-augmented generation (RAG) and no vector database. The models are downloaded pre-trained and only used for inference. "pgvector" appears only as the Docker image name; the extension is never used by the code.

1.3 Explaining the project: 30 seconds, 2 minutes, 5 minutes

These scripts only use verified facts. Practise saying them in your own words; don't recite them.

30-second version

"It's a Flask web app for classroom attendance with two channels. A webcam kiosk recognises enrolled students with FaceNet embeddings and only marks them after it sees a blink, so a printed photo doesn't work. Students without the kiosk scan a QR code that rotates every five seconds and is cryptographically signed, which limits forwarding. It uses PostgreSQL through SQLAlchemy, JWT and session auth for admins, Prometheus metrics, Docker, and it's deployed on Render."

2-minute version

"The problem is slow and cheatable roll-call. An admin enrolls a student by entering their details and capturing five face samples. For each sample the server runs MTCNN to find the face, crops it, and runs a pre-trained InceptionResnetV1 network to get a 512-number embedding. It averages the five into one unit-length vector and stores it.

At the door, the kiosk page keeps sending small JPEG frames, one at a time: it sends the next frame about 30 ms after each reply. On every fourth frame the server runs detection and recognition; in between it uses OpenCV CSRT trackers, which are much cheaper. Recognition is one matrix multiplication of all stored vectors against the new one: because every vector has length 1, the dot product equals cosine similarity, and a score of 0.70 or more counts as a match. The browser then watches the eye region of that face and records attendance only after a blink.

The QR path: the teacher's screen fetches a new signed token every five seconds and shows it as a QR code. The phone page validates the token, looks up the roll number, and submits. The server accepts tokens up to 35 seconds old and allows one record per student per day.

Admins sign in with a scrypt-hashed password and get both a session cookie and a JWT. Failed logins lock the account for 15 minutes. It's tested with 53 pytest tests, runs under Gunicorn, has Docker, Compose and Kubernetes files, CI on GitHub Actions, and a live deployment on Render."

5-minute version (structure)
  1. Problem and users (30 s). Proxy attendance, slow roll-call; admins, students at the kiosk, students on phones.
  2. Architecture (60 s). Flask monolith, 3 blueprints, SQLAlchemy models, AI module, vanilla-JS pages; draw the diagram from 1.5.
  3. Face pipeline (90 s). Enrollment → 5 embeddings → centroid. Kiosk → keyframe detection every 4 frames + CSRT tracking → matrix match → browser blink check → /mark_attendance.
  4. QR pipeline (45 s). Signed timestamped token, 5 s rotation, 30/35 s acceptance windows, roll lookup gated by the token, one record per day.
  5. Security and reliability (45 s). Hashed passwords, lockout via cache with Redis fallback, first-admin-only signup, SameSite cookies, JSON errors, metrics.
  6. Honest limitations and next steps (30 s). Blink check is client-side and can't stop a video replay; QR tokens can be shared within 35 s; embeddings are re-read from the database on every keyframe (the real bottleneck at scale); no DB-level unique constraint. Improvements in 2J.

1.5 High-level architecture

Think of the system as four layers: browsers (admin pages, kiosk, student phones), one Flask application containing the routes and the AI code, a database, and optional supporting services (Redis, Prometheus). Everything runs in one Python process; there are no separate microservices.

The primary flows in one paragraph each

  • Enroll: form → POST /register creates the student and roll number (e.g. 2026CSE001) → capture page sends 5 frames to POST /capture_face (each returns one embedding) → POST /save_face_data stores their average. Details in 2B.
  • Face check-in: kiosk loop → POST /recognize_with_box (detect/track/match) → browser blink check → POST /mark_attendance with method: "Face". Details in 2B.
  • QR check-in: GET /generate_qr_token every 5 s on the teacher's screen → phone opens /qr_mobile?token=… → /verify_qr_token, /verify_student, /get_student → POST /mark_attendance with method: "QR". Details in 2B.

1.6 Set up and run it yourself

These steps come from README.md, Makefile, Dockerfile and the CI file. Your Windows machine already has a venv folder (Python 3.10.11).

Prerequisites

  • Python 3.10 (the version used by the Dockerfile and CI).
  • A database. PostgreSQL for a production-like setup, or SQLite for a quick local run (set DATABASE_URL=sqlite:///attendance.db). The database must be reachable at startup because create_app() calls db.create_all().
  • Internet on first run of face features: facenet-pytorch downloads the VGGFace2 weights the first time the embedding model is used.
  • Optional: Redis, Docker.

Install

python -m venv venv
venv\Scripts\activate            # Windows (macOS/Linux: source venv/bin/activate)
pip install --upgrade pip
pip install torch==2.14.1 torchvision==0.29.1 --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements-dev.txt

PyTorch is installed separately from requirements.txt because the CPU-only build is much smaller. Since 2.5.0 they are pinned to the same versions in the Dockerfile, CI, Makefile and README. Set SECRET_KEY in .env before starting the app. A venv created before 2.5.0 (NumPy 2.2.6, OpenCV 4.13.0.92, torch 2.11.0) does not match the pins; reinstall with the commands above.

Configure

copy .env.example .env           # macOS/Linux: cp .env.example .env
# then edit .env: set SECRET_KEY to a long random value and DATABASE_URL to your database

All settings and their defaults are listed in 2G.

Run

python run.py                    # Windows: Flask's built-in server; Linux/macOS: Gunicorn
# open http://localhost:5000 and use "Initialize Admin Profile" to create the first admin

Test

python -m pytest -v
python -m pytest --cov=app --cov-report=term-missing

The tests use an in-memory SQLite database and never touch your real database or Redis tests/conftest.pyTestConfigL22–38↗.

Full stack with Docker Compose

docker compose up -d --build     # app :5000, Postgres :5432, Redis :6379, Prometheus :9090, Grafana :3000
Camera and QR need the right URL

Browsers only allow webcam access on https:// pages or on localhost. The QR code encodes the server's own URL for /qr_mobile (built with url_for, https behind a proxy) app/templates/qr_session.htmlL77↗, so if the teacher opens the app at http://localhost:5000 the QR points at "localhost", which a phone cannot reach. The QR flow therefore really works on a deployed HTTPS address such as your Render URL.

Status: the core flows work. During this analysis they were run end to end with the real MTCNN/FaceNet models: enrollment, recognition (confidence 0.967 for the enrolled test face), QR check-in on a phone-sized browser, records, CSV export and purge. A static photo fed as a webcam was not marked present; a clip with a simulated blink was. CI on GitHub Actions passes on commit cb32952. Most important limitations (full list in 2J):

  • The blink check runs in the browser, so the server trusts any signed-in kiosk; a video of a blinking student is not detected.
  • A QR token is valid for up to 35 seconds for anyone who has it, so it can still be shared quickly, and the student is not authenticated (they type a roll number).
  • On every detection frame the server loads and JSON-parses every student's embedding. Measured in the analysis sandbox: parsing 10,000 embeddings took about 1.3 s, while the matrix product took about 1.1 ms.
  • "One record per student per day" is enforced by application code, not by a database constraint.
  • In-memory state (kiosk trackers; lockout counters without Redis) is per process.

2B. Architecture and system workflow

Core understanding

A web application is a program that waits for HTTP requests (a browser asking "give me this page" or "save this data") and sends back responses (HTML pages or JSON data). This project is a monolith: one program does everything (pages, API, AI, database access). Inside it, code is grouped by responsibility: routes (what URL does what), models (database tables), AI (face maths) and helpers.

Implementation mastery

Flask maps each URL to a Python function with @blueprint.route(...). Three blueprints split the routes by feature. Models are SQLAlchemy classes. The AI code is plain functions called by the routes. Browser pages are Jinja2 templates plus one JavaScript file each, and they talk to the server using fetch() with JSON.

Advanced interview extension

A monolith is the right call at this size: one deployment, no network calls between services, simple transactions. The cost is that the CPU-heavy face pipeline shares a process with cheap requests like login, so a busy kiosk can slow everything down. A natural split, if needed, would move /recognize_with_box into a separate inference service that scales independently (see 3E).

Startup sequence: what happens when you run python run.py

  1. Import time. run.py imports app. That imports app/config.py (loads .env, then reads environment variables into the Config class) and app/extensions.py (creates db and cache; if REDIS_URL is set, it tries to PING Redis with a 1-second timeout).
  2. app/__init__.pycreate_app()L12–59↗ runs (because run.py calls it at module level):
    1. Creates the Flask app and copies the config.
    2. Warns if the development SECRET_KEY is in use.
    3. db.init_app(app) attaches SQLAlchemy.
    4. Imports the models so their tables are known.
    5. Imports the route modules. Importing attendance.py imports app/ai/facenet_model.py, which imports PyTorch (slow, a few seconds) and sets it to 1 thread, but does not load the networks yet.
    6. Registers the blueprints. This also registers app/routes/main.pyblock_unauthorized()L190–210↗ as a before-request hook.
    7. app/metrics.pyinit_metrics()L41–69↗ adds the timing hooks and /metrics.
    8. db.create_all() connects to the database and creates missing tables. If the database is down, startup fails here.
  3. Server start. run.pyL8↗ picks the port. On Windows: Flask's server. On Linux (Docker, Render): Gunicorn with 1 worker and 4 threads run.pyStandaloneApplicationL16–28↗.
  4. First face request. The first call to mtcnn.detect builds MTCNN; the first embedding builds InceptionResnetV1, which downloads the VGGFace2 weights (a file of about 110 MB) if they are not cached. That first kiosk or enrollment request is therefore slow. This happened during this analysis.
  5. Shutdown. There is no custom shutdown code. Gunicorn stops the worker; database connections and in-memory state (trackers, fallback cache) are simply discarded.

The life of one request

Error handling pattern. There is no global error handler. Instead, most API views wrap their body in try/except, log the exception, roll back the database session, and return a JSON error (usually HTTP 500). Two endpoints deliberately return HTTP 200 with an error field for "no usable face" so the browser loop keeps going: app/routes/attendance.pyrecognize_with_box()L94–235↗ and app/routes/student.pycapture_face()L149–213↗. An exception outside those blocks would produce Flask's default HTML 500 page.

User journeys traced through the code

Journey 1: first admin, sign-in and sessions
  1. GET / → app/routes/main.pyhome()L292–296↗. Already signed in? Redirect to /dashboard. Otherwise render the login page with allow_admin_signup = admin_signup_open(), which is true only when ALLOW_PUBLIC_ADMIN_SIGNUP is set or no admin exists yet app/routes/main.pyadmin_signup_open()L285–289↗.
  2. The inline script in app/templates/admin_login.htmlL199↗ posts JSON to /register_admin or /login_admin.
  3. Register app/routes/main.pyregister_admin()L450–494↗: refuse (403) unless signup is open or the caller is already an admin; validate the email (format, ≤120 chars) and password policy; reject duplicates; store generate_password_hash(password).
  4. Login app/routes/main.pylogin_admin()L497–552↗: validate input → if locked, 403 → look up the admin → check_password_hash. Success: clear the failure counter, put {"admin": email} in the session cookie, and also return a JWT. Failure: app/routes/main.pyrecord_failed_login()L160–168↗; at the threshold (3) answer 403 "locked", otherwise 401 with attempts left. Unknown emails are counted too, so responses don't reveal which emails exist.
  5. Where the session lives. Flask's default session is a signed cookie (no server-side session table). The browser holds {"admin": "…"}, signed with SECRET_KEY, marked HttpOnly and SameSite=Lax app/config.pyL47↗. The web pages never use the JWT; it is for API clients such as scripts or Postman.
  6. Logout clears the cookie app/routes/main.pylogout()L555–560↗. A JWT already issued stays valid until it expires (24 h).
Journey 2: enrolling a student and capturing their face
  1. The admin fills the form; app/static/js/register.jsregister()L23–96↗ posts JSON to /register.
  2. app/routes/student.pyregister()L106–145↗ validates (app/routes/student.pyvalidate_student_fields()L66–102↗), rejects a duplicate email, computes the next roll with app/routes/student.pygenerate_roll()L42–63↗ (e.g. year 2026 + CSE + 001), inserts, and returns {"status": "success", "roll": "2026CSE001"}.
  3. The browser saves the roll in localStorage and opens /capture.
  4. app/static/js/capture.jsrunEnrollmentLoop()L120–214↗ captures a full-resolution JPEG (quality 0.9) every 650 ms and posts it to /capture_face.
  5. app/routes/student.pycapture_face()L149–213↗: base64 → bytes → cv2.imdecode → BGR image → convert to RGB → mtcnn.detect → take the largest face (MTCNN sorts by size) → reject if probability < 0.90 or smaller than 40 px → crop → app/ai/facenet_model.pyget_embedding_from_crop()L74–118↗ → return the 512 numbers and the box.
  6. After 5 successes the browser posts all five vectors to /save_face_data. app/routes/student.pysave_face_data()L234–274↗ validates them, averages them (the centroid), rescales the average to length 1, and stores it as JSON text on the student row.
Design detail worth discussing in interviews

Embeddings travel from server to browser and back. The server trusts the browser to send back real vectors (it checks only shape and that values are finite numbers). A cleaner design keeps the samples on the server, for example keyed by roll in the cache, so a modified client cannot plant an arbitrary vector. This matters little here because only admins can call these endpoints.

Journey 3: face check-in at the kiosk (the hot path)
  1. Browser loop. app/static/js/recognize.jsdetectLoop()L249–422↗ draws the video into a 380-pixel-wide canvas, encodes JPEG at quality 0.6 (about 10 KB, measured), and posts it with a per-tab client_id.
  2. Server, every frame. app/routes/attendance.pyrecognize_with_box()L94–235↗ decodes the image, returns early with status: "low_light" if the average grey level is below 35, then fetches this kiosk's tracker state from app/routes/attendance.pyget_client_tracker_session()L48–67↗.
  3. Keyframes (frame counter divisible by 4, or no active trackers): run MTCNN; load every enrolled vector (app/routes/attendance.py_load_student_profiles()L81–90↗); for each detected face that passes the filters (probability ≥ 0.90, at least 45×45 px, not a flat crop), compute its embedding, find the best match with app/ai/comparator.pyvectorized_matrix_match()L47–86↗, and start a CSRT tracker labelled with the roll (or "Unknown").
  4. Every frame: each tracker updates its box on the new frame; failed or tiny boxes are dropped. The response lists roll, confidence, is_unknown and box for each face.
  5. Liveness in the browser. For each recognised roll, app/static/js/recognize.jsanalyzeEyeLiveness()L108–154↗ measures pixel variance in the eye band of that face (only on fresh boxes). A blink = variance dips below 88% of its recent average and recovers above 92% within 40–1200 ms.
  6. Marking. Once a face is live and not yet marked in this session, app/static/js/recognize.jsmarkFaceAttendance()L209–245↗ posts {roll, method: "Face"}. app/routes/attendance.pymark_attendance()L239–305↗ requires admin credentials for the Face method (the kiosk's session cookie), looks the student up, checks for a record with the same roll and IST date, inserts one, and increments attendance_marked_total.

Why the box labels stay stable: the label is decided on the keyframe and carried by the tracker until the next keyframe, so recognition runs at most once every 4 frames per face.

Journey 4: QR check-in from a phone
  1. Teacher screen. The inline script in app/templates/qr_session.htmlL66↗ calls app/routes/main.pygenerate_qr_token()L248–265↗ every 5 s. The token is URLSafeTimedSerializer.dumps({"nonce", "created_at"}): the JSON payload in base64, a timestamp, and an HMAC signature computed with SECRET_KEY and the salt qr-attendance-token. Since 2.5.0 the server builds the /qr_mobile?token=… URL and returns it as an SVG QR code (qr_svg, rendered with segno); earlier versions built origin + "/qr_mobile?token=…" in the page and asked api.qrserver.com to draw it.
  2. Phone, step 1. app/static/js/qr_mobile.jsverify()L29–91↗ stores the token in sessionStorage (and strips it from the address bar), upper-cases the typed roll, checks the token, then checks the roll with the token attached (app/routes/student.pyverify_student()L288–302↗).
  3. Phone, step 2. /qr_verify fetches the name with the token in an X-QR-Token header (app/routes/student.pyget_student()L306–324↗), then app/static/js/qr_verify.jsconfirmAttendance()L40–82↗ submits. app/routes/attendance.pymark_attendance()L239–305↗ re-checks the token (≤ 35 s), finds the student case-insensitively, applies the one-per-day rule and inserts.
Signed, not encrypted (SHA-1 before 2.5.0, SHA-256 since)

Anyone can base64-decode the payload and read the nonce and timestamp; the signature only stops changes. itsdangerous signs with HMAC-SHA1 by default (checked in itsdangerous 2.2.0: Signer.default_digest_method is SHA-1), so the "HMAC-SHA256" wording in the README and on the QR page is inaccurate. HMAC-SHA1 is still considered safe for message authentication; 2.5.0 switched to URLSafeTimedSerializer(secret, salt=…, signer_kwargs={"digest_method": hashlib.sha256}) so the code matches the docs. The nonce is never checked: it only makes each token unique.

Journey 5: dashboard, records, CSV export and purge
  • Dashboard numbers: app/routes/attendance.pydashboard_data()L425–453↗ counts students and the distinct rolls with a record on today's IST date in a single SQL query, then absent = total − present.
  • Records: app/routes/attendance.pyget_records()L309–342↗ loads all records (newest first), keeps one per roll per day, and groups them as {"YYYY-MM-DD": [{roll, method, time}]}. This loads the whole table: fine for a class, slow for years of data (no pagination).
  • CSV export: app/routes/attendance.pyexport_records()L346–407↗ joins attendance with students (outer join, so records for deleted students show "N/A"), applies optional date, dept and roll filters, and streams a CSV with a timestamped filename. A bad date returns 400.
  • Purge: app/routes/attendance.pyclear_records()L411–421↗ deletes every attendance row (POST, admin only). There is no undo and no audit log.

PyTorch and facenet-pytorch: running the face models
Core understanding

PyTorch is a library for running (and training) neural networks. facenet-pytorch packages two ready-made face networks for PyTorch: MTCNN finds faces in a picture; InceptionResnetV1, trained by others on the VGGFace2 dataset of celebrity faces, turns a face into 512 numbers so that photos of the same person give similar numbers.

In this project

Interview extension

OpenCV: image handling and object tracking
Core understanding

OpenCV is a large computer-vision library. Here it decodes JPEG bytes into a pixel array, converts colour formats, resizes images and tracks moving boxes between frames.

In this project

cv2.imdecode and cv2.cvtColor in both capture and recognition; cv2.resize(…, INTER_AREA) to 160×160 before embedding; CSRT (Channel and Spatial Reliability Tracker) per face, with fallbacks to the legacy API or the faster, less accurate KCF tracker app/routes/attendance.py_create_tracker()L70–78↗. Interview extension

OpenCV loads images as BGR (blue-green-red) while the face models expect RGB; forgetting the conversion silently lowers accuracy. Trackers are stateful C++ objects held in Python memory per kiosk, which is why the recognition endpoint is not stateless and cannot be load-balanced freely across pods without "sticky" routing. NumPy: fast vector maths
Core understanding

NumPy stores numbers in compact arrays and runs maths on whole arrays at once in fast compiled code, instead of looping in Python.

In this project

Normalising embeddings (np.linalg.norm), averaging the five samples (np.mean(axis=0)), and matching: np.vstack builds an N×512 matrix and np.dot(matrix, query) gives all N similarity scores in one call, then np.argmax picks the best app/ai/comparator.pyvectorized_matrix_match()L47–86↗. Under the hood np.dot calls a BLAS library (Basic Linear Algebra Subprograms) that uses SIMD CPU instructions.

Interview extension

Complexity is O(N·d) with N students and d = 512 either way; the gain over a Python loop is a constant factor. Measured in the sandbox: about 0.14 ms for N = 1,000, 1.1 ms for N = 10,000, 9.5 ms for N = 50,000. Beyond millions of vectors, approximate nearest-neighbour indexes (FAISS, HNSW in pgvector) become worthwhile. The current code rebuilds the matrix from JSON on every keyframe, which costs far more than the dot product (see 2H).

itsdangerous: tamper-proof, time-limited QR tokens
Core understanding

A signature is a short code computed from the data and a secret key. Anyone can read signed data, but nobody without the key can change it without the signature failing. A timed signature also includes when it was made, so the server can reject old ones.

In this project

URLSafeTimedSerializer(SECRET_KEY, salt="qr-attendance-token") app/routes/main.pyget_qr_serializer()L224–226↗. dumps() creates tokens; loads(token, max_age=…) verifies signature and age, raising SignatureExpired or BadSignature app/routes/main.pycheck_qr_token()L229–245↗. The salt separates QR tokens from other things signed with the same key (Flask signs the session cookie with that key too, under a different salt).

Interview extension

Default algorithm: HMAC-SHA1 (not SHA-256 as the docs say). Verification needs no database lookup, so it is fast and horizontally scalable; the trade-off is that tokens cannot be revoked or made single-use without storing state. A JWT could do the same job; itsdangerous is lighter and already bundled with Flask.

PyJWT: tokens for API clients
Core understanding

A JWT (JSON Web Token) is a signed piece of JSON (like "user X, expires at time Y") that a client sends in the Authorization: Bearer … header. The server checks the signature instead of looking anything up.

In this project

Created at login with claims sub (email), role, iat, exp (24 h), signed with HS256 and SECRET_KEY app/routes/main.pygenerate_jwt_token()L48–59↗. Checked first by app/routes/main.pyadmin_required()L91–123↗; expired → 401 "expired", bad signature → 401 "invalid". Interview extension

Stateless tokens can't be revoked before expiry (logout does not invalidate them), the role claim is never checked (every admin is equal), and the same secret signs JWTs, sessions and QR tokens, so leaking it compromises all three. Redis and SafeCacheStore: shared counters with a fallback
Core understanding

Redis is an in-memory key-value store that many processes can share over the network, with automatic expiry of keys. Here it answers "how many wrong passwords has this email typed recently?" for every server process at once.

In this project

app/extensions.pySafeCacheStoreL32–131↗ offers set/get/delete with optional expiry. With Redis: values live in Redis. Without it (or during an outage): a module-level dict with expiry timestamps. Interview extension

The read-modify-write increment is not atomic; under parallel guessing a few extra attempts can slip through. Redis INCR + EXPIRE (or a Lua script) would make it atomic. That is a deliberate trade-off: logins keep working.

Core understanding

Flask's built-in server is for development. Gunicorn is a production server for Python web apps: it manages worker processes and threads that handle requests in parallel.

In this project

Interview extension

Why one worker? 2E. The AI pipeline: face detection, embeddings and matching

What kind of AI is this?

AI (artificial intelligence) is the broad goal of making computers do tasks that seem to need intelligence. Machine learning (ML) is one way to get there: learn patterns from data instead of writing rules by hand. Deep learning is ML with many-layered neural networks. This project uses two pre-trained deep-learning models for inference only: it runs them, it never trains or fine-tunes them. There is no LLM, no prompts, no tokenisation, no retrieval-augmented generation (RAG) and no vector database. The blink check is a hand-written rule, not ML.

From camera pixels to a name: the full pipeline

Step 1: finding faces with MTCNN
Core understanding

Before you can recognise a face you must find it. MTCNN (Multi-task Cascaded Convolutional Networks) scans the picture at several sizes with three small neural networks in a row: a fast one proposes many candidate boxes, a second one rejects most of them, a third one gives final boxes, a confidence score, and five landmark points (eyes, nose, mouth corners).

Implementation mastery

Configured in app/ai/facenet_model.pyget_mtcnn()L27–43↗ with min_face_size=20 (ignore faces smaller than 20 px), stage thresholds [0.6, 0.7, 0.7] and keep_all=True (return every face). Called as mtcnn.detect(rgb), which returns (boxes, probs); boxes is None when nothing is found. The library sorts boxes largest-first, which is why enrollment can safely take boxes[0] app/routes/student.pycapture_face()L149–213↗. The app then applies its own filters: probability ≥ MTCNN_CONFIDENCE_THRESHOLD (0.90), size ≥ 40 px (enrollment) or 45 px (kiosk), and pixel standard deviation ≥ 18 (rejects flat, featureless crops). The five landmarks are never requested.

Interview extension

Measured cost in the sandbox: about 58 ms per 380×285 frame on one CPU thread, which is why detection runs only on every 4th kiosk frame. The unused landmarks are a missed opportunity: they give exact eye positions, which would make the blink check (currently a fixed band at 18–46% of box height) far more precise, and they allow face alignment (rotating so the eyes are level), which usually improves recognition accuracy.

Step 2: turning a face into 512 numbers (embedding)
Core understanding

An embedding is a list of numbers that summarises something so that similar things get similar lists. Think of it as GPS coordinates for faces in a 512-dimensional space: photos of the same person land close together, different people land far apart. The network learned this from millions of labelled face photos (the VGGFace2 dataset) before you ever downloaded it.

Implementation mastery

app/ai/facenet_model.pyget_embedding_from_crop()L74–118↗: convert BGR→RGB, resize the crop to 160×160 with area interpolation, convert to a PyTorch tensor shaped (1, 3, 160, 160), scale pixels with (x − 127.5) / 128 to about [−1, 1] (the "fixed image standardisation" this model expects), run InceptionResnetV1(pretrained="vggface2") under torch.no_grad(), and divide by the vector's length so it has length 1 (L2 normalisation). The network already normalises its output, so the app's extra normalisation is redundant but harmless. On any error it logs and returns None. Measured: about 57 ms per face on the sandbox.

Interview extension

"FaceNet" is the 2015 Google paper that introduced learning face embeddings with a triplet loss; this project uses facenet-pytorch's InceptionResnetV1 port with weights trained on VGGFace2. Pre-trained models inherit their training data's biases (for example uneven accuracy across demographics) and can be weaker on low-resolution webcam images; the repository contains no evaluation measuring this.

Step 3 (enrollment): averaging five samples into one profile

Five embeddings from slightly different head angles are averaged: c = mean(v₁…v₅), then rescaled to length 1 app/routes/student.pysave_face_data()L234–274↗. The average sits in the middle of that person's cluster, so a new photo from any of those angles is likely to be close to it. Trade-off: one vector per student keeps storage and matching simple (N rows, not 5N), but loses information; storing all five and taking the best match is a common alternative. Re-enrolling overwrites the old profile.

Step 4: matching with cosine similarity in one matrix multiplication
Core understanding

Cosine similarity measures the angle between two vectors: 1 means pointing the same way (very similar), 0 means unrelated. For vectors of length 1, cosine similarity is simply the dot product (multiply matching positions, add them up).

Implementation mastery

app/routes/attendance.py_load_student_profiles()L81–90↗ reads every student that has an embedding, parses the JSON, and skips any vector that is not 512 long. app/ai/comparator.pyvectorized_matrix_match()L47–86↗ stacks them into a matrix E (N×512), computes scores = E · q (N numbers at once), takes the index of the highest score, and returns that roll if the score is at least FACE_MATCH_THRESHOLD (0.70), otherwise None ("Unknown"). Worked example with 3-number vectors: q = (0, 1, 0); students A = (1, 0, 0), B = (0, 1, 0) → scores (0, 1) → B with score 1.0. This exact case is a unit test tests/test_vector.pyL51↗.

Interview extension

Threshold meaning: for unit vectors, Euclidean distance d and cosine similarity s are linked by d = √(2 − 2s). So s ≥ 0.70 means d ≤ 0.775. Many FaceNet-style setups accept distances around 1.0–1.1, so 0.70 is on the strict side: fewer wrong matches (false accepts), more misses (false rejects). The repository has no labelled evaluation set, so the threshold is not empirically calibrated; to calibrate it you would collect genuine and impostor pairs, plot false-accept vs false-reject rates against the threshold, and pick a point. Open-set problem: argmax always picks someone; the threshold is what turns strangers into "Unknown".

Step 5 (kiosk): keyframes plus tracking

Running detection + embedding on every frame costs roughly 58 ms + 57 ms per face on the sandbox CPU. Instead, app/routes/attendance.pyrecognize_with_box()L94–235↗ runs the full pipeline on frames where frame_count % 4 == 0 (or when no tracker is alive) and creates one OpenCV CSRT tracker per recognised face. On the other frames each tracker only predicts where its box moved (about 23 ms per face, measured), and keeps the label it got on the keyframe. Trade-off: a label can be stale for up to three frames, and if two people swap places quickly between keyframes the labels can follow the wrong person until the next keyframe.

Step 6 (kiosk): the blink liveness check
Core understanding

A presentation attack is showing the camera a fake: a printed photo, a phone screen. Liveness detection tries to tell a real person from a fake. This project asks for a blink, because a printed photo cannot blink.

Implementation mastery

In the browser, for each recognised roll, app/static/js/recognize.jsanalyzeEyeLiveness()L108–154↗ takes a band of the face box (from 18% down, 28% tall, 76% wide), converts its pixels to grey, and computes their variance (how much brightness varies). Open eyes have dark pupils and bright whites, so variance is high; closed lids are uniform skin, so variance drops. It keeps the last 8 readings; a reading below 88% of their average starts a "dip", and a reading back above 92% within 40–1200 ms counts as a blink and marks that roll as live. Only after that does the kiosk call /mark_attendance. During this analysis a static photo used as the webcam was never marked, while a clip with a simulated blink (eye band blurred for 400 ms) was.

Interview extension

Weaknesses: it runs on the client, so the server cannot verify that a blink happened (a modified kiosk or a direct API call with an admin token can mark anyone); a video of the student blinking defeats it; lighting changes, glasses and head movement can cause false blinks; the "eye band" is a fixed fraction of the box rather than real eye positions. Better options, in increasing cost: use MTCNN's eye landmarks; compute a true Eye Aspect Ratio (EAR) from a 68-point landmark model; run a passive anti-spoofing CNN on the server; use depth or infrared cameras. Note: the original documentation called this "EAR", but there are no landmarks, so it is a variance heuristic, not EAR.

Running the models: where, how fast, at what cost

  • Local inference: everything runs inside the Flask process on CPU (GPU is used automatically only if CUDA is available). No external AI API is called, so there is no per-request cost and no face data leaves the server, apart from the model download.
  • Model download: on first use facenet-pytorch downloads 20180402-114759-vggface2.pt (≈112 MB) from the library's GitHub releases into the PyTorch cache. A container that restarts with an empty cache downloads it again; baking it into the Docker image would avoid that.
  • Measured in the analysis sandbox (2 vCPU, PyTorch on 1 thread): MTCNN 58 ms per frame, embedding 57 ms per face, CSRT update 23 ms per face, JPEG decode 0.6 ms, kiosk JPEG ≈ 10 KB, recognition confidence for the enrolled test face 0.967.
  • Memory: PyTorch plus both models takes hundreds of megabytes, the reason for one Gunicorn worker on a 512 MB plan.

How good is the recognition? (honest answer)

The repository has no evaluation: no dataset, no accuracy, false-accept or false-reject numbers. The tests check the maths with toy vectors and check that the pipeline runs (low-light and empty-scene frames). During this analysis one public sample face was enrolled and recognised with 0.967 similarity, which shows the pipeline works but says nothing about accuracy across many people. In an interview, say exactly that, and describe how you would evaluate it (see question on evaluation).

2I. Software engineering and design decisions

For each decision: what the code does, why it is reasonable (with evidence), what else could have been done, and when the alternative would win.

Application factory + blueprints (modularity)

Choice: app/__init__.pycreate_app()L12–59↗ builds the app; routes are split into three blueprints by feature. Why: tests create isolated apps with their own config (create_app(TestConfig)), and features live in separate files. Cohesion check: main.py mixes four jobs (auth, page routes, QR tokens, validators); splitting it into auth.py, qr.py and pages.py would raise cohesion. Coupling: the other blueprints import helpers from main.py, so main.py has become a shared utility module; moving helpers to app/security.py would make dependencies clearer.

Decorator for authorisation

Choice: app/routes/main.pyadmin_required()L91–123↗ wraps view functions (the decorator pattern: add behaviour around a function without changing it). Why: one line per protected route, one place to change the rules. Alternative: Flask-Login or Flask-JWT-Extended provide the same with tested edge cases; a before_request hook on whole blueprints avoids forgetting a decorator. Watch out: the JSON-vs-redirect decision by URL prefix is easy to break when adding routes.

Lazy singletons + a proxy for the models

Choice: one shared MTCNN and one InceptionResnetV1 per process, created on first use with double-checked locking app/ai/facenet_model.pyget_mtcnn()L27–43↗; app/ai/facenet_model.pyMTCNNProxyL61–68↗ lets other modules import mtcnn at startup without loading anything. Why: models are expensive (memory, load time); creating them per request would be far too slow, and loading at import would slow every startup and every test. Trade-off: the first face request pays the load cost (and the weight download). Alternative: load eagerly in a startup hook (predictable latency, slower boot), or run models in a separate inference service.

Graceful degradation: cache with fallback

Choice: app/extensions.pySafeCacheStoreL32–131↗ prefers Redis and silently falls back to memory, re-probing every 30 s (a simple form of the circuit breaker idea: stop hammering a failing dependency, try again later). Why: logins must keep working even if Redis is down; Redis is optional for local development. Trade-off: availability over consistency. During an outage counters aren't shared, and memory writes are not copied back to Redis afterwards. When to choose differently: if the cache held something that must be consistent (for example single-use tokens), failing closed (rejecting requests) would be safer.

Stateless tokens vs server-side state

Choice: admin web sessions are signed cookies, API access uses JWTs, QR codes use signed timed tokens: none of them needs a database lookup. Why: fast, nothing to store, works across multiple servers sharing the key. Trade-off: you can't revoke one token or make it single-use without adding state. When server-side state wins: when you need logout-everywhere, per-device QR binding, or audit of who used which token.

Amortising expensive work: keyframes, tracking, vectorisation

Keyframes + tracking: pay the 100+ ms detection/recognition cost on 1 frame in 4 and the cheaper tracker cost on the rest (app/routes/attendance.pyrecognize_with_box()L94–235↗). Vectorisation: one np.dot over an N×512 matrix instead of N Python-level comparisons (app/ai/comparator.pyvectorized_matrix_match()L47–86↗). Both are classic trade-offs of freshness or accuracy for throughput. Their weak spot is that the matrix is rebuilt from the database on each keyframe; see 2H.

Concurrency: threads, locks and races

Gunicorn serves 4 requests at once in threads of one process. Shared mutable state and how it's protected:

API design style

Endpoints are verb-style (/mark_attendance, /clear_records, /get_student/<roll>), not resource-style REST (POST /attendance, DELETE /attendance, GET /students/<roll>). Verb-style is easy to read for a small app with one client; REST makes caching, documentation and consistency easier as the API grows. Response bodies are inconsistent (message vs error; status strings like "already marked today"), and there is no API versioning.

Persistence choices
  • Embeddings as JSON text: works on any database including SQLite, human-readable; costs ~11 KB per student and a parse on every read. Alternatives: binary (LargeBinary of 2 KB float32), PostgreSQL arrays, or pgvector with an index (worth it only at very large N or if searching inside the database).
  • Naive IST timestamps: make "today" simple for one time zone; break if the institution spans zones or if code ever mixes in UTC times. The common alternative is storing UTC with time-zone-aware datetimes and converting for display.
  • No migrations: fine for a prototype, risky once real data exists.

2J. Limitations, risks and future improvements

Confirmed limitations (seen in the code)

  1. Liveness is client-side; the server cannot verify a blink, and video replays pass.
  2. QR tokens can be reused by anyone for up to 35 s; students are identified only by the roll number they type.
  3. Every keyframe re-reads and re-parses all embeddings (O(N) database load and JSON parsing).

  7. QR images depend on a third-party service, which also receives the short-lived check-in URLs.
  8. No evaluation of recognition accuracy; threshold not calibrated against data.

  10. Unpinned torch and transitive packages; no lockfile; dev tools in runtime requirements.

Problem: check-then-insert in app/routes/attendance.pymark_attendance()L239–305↗ can double-insert under concurrency. Direction: add an attendance_date column (IST date) with UNIQUE(roll, attendance_date); insert directly and catch IntegrityError → "already marked today". Needs a migration and a clean-up of existing duplicates. Trade-off: slightly more schema; much stronger guarantee. Test: fire two concurrent requests (threads) for the same roll and assert exactly one row.

Detail: #5 server-side liveness

Problem: the server trusts the kiosk's blink decision. Direction options: (a) send a short burst of frames with the mark request and re-run the blink check on the server; (b) a passive presentation-attack-detection CNN on face crops; (c) random challenges ("turn left") checked server-side. Trade-off: more CPU per check, possible false rejections of real students; dedicated hardware (depth/IR cameras) is the strongest but costs money. Test: a labelled set of real and spoof videos; measure attack acceptance and genuine rejection rates.

Detail: #4 measure recognition accuracy

Problem: nobody knows how often the system confuses two students or misses one. Direction: collect consenting samples (several photos per person), compute embeddings, form genuine pairs (same person) and impostor pairs (different people), and plot false-accept rate (FAR) vs false-reject rate (FRR) across thresholds; also test identification accuracy (top-1) with the centroid approach. Trade-off: needs data collection with consent and privacy care. Success: a chosen threshold with documented FAR/FRR.

Q18. How are roll numbers generated, and what happens if two admins enroll at the same moment? Intermediate

Direct answer

Roll = year + department (upper-case) + next number, zero-padded to 3 digits (2026CSE001). The next number is the highest existing one for exactly that prefix, plus 1. If two requests compute the same roll, the unique index on students.roll rejects the second insert; the code rolls back and recomputes, up to 5 attempts.

Q28. Did you train a model? What kind of AI is this? Basic

Direct answer

No training. It uses two pre-trained deep-learning models for inference: MTCNN for face detection and InceptionResnetV1 (VGGFace2 weights) for 512-dimensional face embeddings. Recognition is nearest-neighbour search with cosine similarity. No LLM, no RAG.

Q29. What is an embedding, and why 512 dimensions? Basic

Direct answer

A vector of numbers that places similar faces close together. 512 is simply the size of this model's output layer: enough capacity to separate many identities, small enough to compare quickly (2 KB as float32).

Foundation

The model was trained so that images of the same person map to nearby points and different people to distant points; we only use the trained mapping.

Q30. Why is a dot product the same as cosine similarity here? Intermediate

Direct answer

cos θ = (a·b) / (|a||b|). The code normalises every vector to length 1, so the denominator is 1 and cos θ = a·b. That lets one matrix–vector product score every student at once.

Evidence

Normalisation in app/ai/facenet_model.pyget_embedding_from_crop()L74–118↗ and app/routes/student.pysave_face_data()L234–274↗; product in app/ai/comparator.pyvectorized_matrix_match()L47–86↗.

Follow-up

"Relationship to Euclidean distance?" For unit vectors |a − b|² = 2 − 2(a·b), so ranking by distance and by cosine gives the same order.

Q31. How did you pick the 0.70 threshold? What happens if you change it? Advanced

Direct answer (honest)

It's a configured default (FACE_MATCH_THRESHOLD), not calibrated on data in this repository. Raising it reduces false accepts (wrong person marked) but increases false rejects (real student shown as Unknown); lowering it does the opposite.

Reasoning

0.70 cosine ≈ Euclidean 0.775 between unit vectors, stricter than distances often used with FaceNet-style models, so expect more "Unknown" than wrong names. For attendance, a false accept (marking an absent student) is usually worse than a false reject (the student rescans or uses QR).

Q32. How accurate is your recognition, and how would you measure it? Advanced

Direct answer (honest)

I haven't measured accuracy; the repo has no evaluation set. In testing, one enrolled sample face was recognised at 0.967 similarity, which shows the pipeline works, not how accurate it is.

How to measure

Collect several images per consenting person. Verification: build genuine pairs (same person) and impostor pairs, compute similarities, and plot false-accept rate and false-reject rate against the threshold; choose an operating point. Identification: enroll with the centroid method, test with held-out images, report top-1 accuracy and the rate of "Unknown" for non-enrolled people. Repeat under low light and with different cameras.

Limitations

Small classroom datasets give noisy estimates; demographic balance matters.

Q37. Explain your liveness detection. Is it secure? Advanced

Direct answer

In the browser, for each recognised student, it measures grey-level variance in an eye band of the face box over the last 8 frames. A dip below 88% of the average that recovers above 92% within 40–1200 ms counts as a blink, and only then is attendance marked. It stops printed photos (verified with a static-photo webcam test). It is not secure against video replays or a modified client, because the server can't verify the decision.

Performance and scaling

Q57. Where is the performance bottleneck as the number of students grows? Advanced

Direct answer

Not the dot product. On every keyframe _load_student_profiles queries all students and JSON-parses each ~11 KB embedding. Measured in the sandbox: ~1.3 s for 10,000 students, vs ~1.1 ms for the matrix product.

Evidence

Fix

Cache the stacked matrix and invalidate it on enrollment changes; store vectors in binary.

Q58. What is the time complexity of matching one face? Intermediate

Direct answer

O(N·d) for N students and d = 512: one multiply-add per number in the matrix, then O(N) for argmax. Building the matrix is also O(N·d) (and currently includes JSON parsing). Memory O(N·d).

Follow-up

"Sub-linear search?" Approximate nearest neighbour indexes (HNSW, IVF in FAISS/pgvector) trade a little accuracy for roughly logarithmic query time; worth it only at very large N.

Q59. How many kiosks can one server handle? Advanced

Reasoning (with stated assumptions)

Assume one face per frame and the sandbox timings: a keyframe costs ≈ 58 + 57 + 23 ≈ 140 ms of CPU; a tracking frame ≈ 23 ms. Average per frame over 4 frames ≈ (140 + 3 × 23) / 4 ≈ 52 ms of CPU. If each kiosk sends ~5 frames/s, it needs ≈ 0.26 CPU-seconds per second. With 2 cores and 4 threads, roughly 6–7 kiosks before saturating, ignoring Python overhead and the embedding-loading cost. These are estimates, not measurements of the full system.

Follow-up

"How would you verify?" Load-test with recorded frames (for example Locust or k6) and watch p95 latency and CPU.

Q60. Why only one Gunicorn worker? Wouldn't more be faster? Advanced

Direct answer

Each worker is a separate process with its own copy of PyTorch and both models (hundreds of MB), which doesn't fit a 512 MB instance; in-memory state (trackers, fallback cache) is also per process. Threads share one copy, and inference releases the GIL in native code. With more RAM and cores, more workers would add throughput, with sticky routing for kiosks.

Evidence

run.pyL32–34↗; torch threads set to 1 in app/ai/facenet_model.pyL14↗.

Q61. With the GIL, do 4 threads actually help? Challenge

Direct answer

Partly. The GIL allows one thread to run Python bytecode at a time, but PyTorch, OpenCV and NumPy release it during heavy native computation, and database/network waits release it too. So a login or records request can proceed while another thread runs inference. Pure-Python work (JSON parsing of embeddings!) holds the GIL and does block others.

Follow-up

"Why torch.set_num_threads(1)?" To stop each request's inference from spawning many internal threads that fight over 1–2 cores (oversubscription).

Q62. How much network bandwidth does a kiosk use? Intermediate

3E. System design and architecture interview preparation

System design interviews ask you to design (or extend) a system out loud: clarify requirements, sketch components, explain data flow, and discuss trade-offs. For SDE-1 candidates the bar is clear reasoning, not memorised diagrams. This section teaches the vocabulary, applies it to this project, then lets you practise.

1. Fundamentals, in plain words

Functional requirements
What the system must do. Here: enroll students, recognise faces, record attendance once per day, QR check-in, view/export records.
Non-functional requirements
How well it must do it: speed, availability, security, cost. Here: kiosk feedback within a fraction of a second, no proxy attendance, runs on a small CPU-only instance.
Scalability
Handling more load by adding resources. Vertical: a bigger machine (what a larger Render plan gives you). Horizontal: more machines behind a load balancer (what the Kubernetes files sketch).
Availability
The fraction of time the system works (99.9% ≈ 43 minutes down per month). One Gunicorn worker on one instance means any crash or restart is downtime.
Reliability
Doing the right thing correctly over time. The one-per-day rule failing under concurrency is a reliability issue.
Latency vs throughput
Latency = time for one request (one kiosk frame ≈ 50–140 ms of CPU in the sandbox). Throughput = requests handled per second across all users. Tracking lowers average latency; more cores raise throughput.
Consistency
Whether everyone sees the same data. The lockout counter in per-process memory (without Redis) is inconsistent across processes; the database is the consistent source for attendance.
Fault tolerance
Continuing to work when parts fail. Implemented examples: Redis fallback, QR fallback for camera problems.
Maintainability

SD-2: Make QR check-in resistant to forwarding and impersonation

Today: signed timed tokens (≤ 35 s), roll typed by the student. Threats: instant forwarding, typing a friend's roll. Options Proposed: (1) student login (SSO) so the roll comes from identity, not a text box; (2) bind token use to a device cookie: one device, one roll per session (Redis set with TTL); (3) shorten windows and rotate faster; (4) location checks (Wi-Fi network or geofence; spoofable, privacy-sensitive); (5) random face check on the phone. Trade-offs: friction vs security; storing state removes statelessness. Test: attempt forwarding scenarios; measure check-in completion time.

SD-3: Design the face-recognition service for 300 kiosks

Requirements: ≤ 300 ms per frame end to end, 1,500 frames/s at peak (estimate), per-kiosk tracking. Design Proposed: stateless HTTP/gRPC front that routes by kiosk id (consistent hashing) to inference workers holding trackers; workers keep class-roster matrices in memory, refreshed by version; GPU batching if available; back-pressure by dropping frames rather than queueing (stale frames are useless). Alternatives: run detection/tracking in the browser (WebAssembly/WebGPU) and send only face crops for recognition, which cuts server CPU and bandwidth. Failure handling: worker loss → kiosk re-detects on another worker; overload → lower frame rate.

SD-4: Design the login rate limiter properly

Today: per-email counter, 3 failures → 15 min, cache with fallback, non-atomic. Improved Proposed: Redis INCR + EXPIRE (atomic) for per-email and per-IP keys; sliding window or token bucket; progressive delays instead of hard lockout (prevents attackers locking out real admins); alerting on spikes. Trade-off: fail-open vs fail-closed when Redis is down. Test: concurrent attempt test; verify that only N attempts succeed per window.

SD-5: Add reporting and an audit trail

Need: who marked what and when, and who purged records. Design Proposed: append-only audit_events table (actor, action, target, timestamp, channel, client info); soft-delete instead of purge; reports from SQL aggregates (per course, per student percentage) with pagination; scheduled CSV exports to storage. Trade-off: more storage and write volume; privacy rules for retention.

Glossary

API
Application Programming Interface: here, the URLs that accept and return JSON.
Blueprint
A Flask group of routes registered on the app; this project has three.
BLAS
Basic Linear Algebra Subprograms: optimised maths routines NumPy uses for np.dot.
Centroid
The average of several vectors; one per enrolled student.
CI
Continuous integration: automatic tests on every push (GitHub Actions here).
Cosine similarity
How aligned two vectors are (1 = same direction); equals the dot product for unit vectors.
CSRF
Cross-Site Request Forgery: another site making your browser send an authenticated request. Mitigated here by SameSite cookies.
CSRT
Channel and Spatial Reliability Tracker: an OpenCV algorithm that follows a box between frames.
Embedding
A vector that represents an input so similar inputs are close; 512 numbers per face here.
GIL
Global Interpreter Lock: lets one thread run Python bytecode at a time in CPython.
HMAC
Hash-based Message Authentication Code: a signature made with a secret key and a hash function (SHA-1 for the QR tokens).
HPA
Kubernetes HorizontalPodAutoscaler: adds/removes pods based on load.
Idempotent
Doing it twice has the same effect as once (marking attendance should be).
Inference
Running a trained model on new input (no learning happens).
IST
Indian Standard Time, UTC + 5:30; attendance timestamps use it.
JWT
JSON Web Token: signed JSON claims sent as Authorization: Bearer ….
Keyframe
A frame where full detection/recognition runs (every 4th here).
L2 normalisation
Dividing a vector by its length so the length becomes 1.
Liveness detection
Checking that a real, present person is in front of the camera, not a photo or video.
MTCNN
Multi-task Cascaded Convolutional Networks: a three-stage face detector.
ORM
Object-Relational Mapper: maps classes to tables (SQLAlchemy).
PaaS
Platform as a Service: hosting where the provider runs servers for you (Render).
Race condition
A bug where the result depends on the timing of concurrent operations.
SameSite cookie
A cookie flag telling browsers not to send the cookie with cross-site requests (Lax: allowed on top-level navigation GETs).
Salt
Random data mixed into a password hash so identical passwords hash differently. (The itsdangerous "salt" is a different idea: a namespace string.)
TTL
Time to live: how long a cached value or token stays valid.
WSGI
Web Server Gateway Interface: the standard connecting Python web apps (Flask) to servers (Gunicorn).
XSS
Cross-Site Scripting: injecting script into a page through unescaped data.
